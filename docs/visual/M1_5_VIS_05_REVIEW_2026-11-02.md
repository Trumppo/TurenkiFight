## How the numbers were produced

All **measured** numbers below come from DOM/Phaser APIs read in the running page (`canvas.getBoundingClientRect()`, backend canvas attributes, `StationScene.cameras.main.zoom`, Phaser Text `.width/.height` of `scoreLabel`, `hudTimer`, `statusLabel`, fighter label P1, player HUD P1), via `benchmarks/out/measureViewport.mjs`. Rendering chain: logical world 384×216 → camera zoom 1.6667 → 640×360 canvas backing → CSS size = backing × cssScale (Phaser `Scale.FIT`, CSS `width:100%` capped at 960px by `#game`, `max-width:960px`). Content CSS box around the canvas is `main` (max-width 1024, padding 16/24, contains h1 + subtitle + canvas + controls).

Everything marked **observed** is what I saw in the opened PNGs; I explicitly separate that from the numbers.

## Visual inspection of the actual PNGs (observed, not measured)

- **1920×1080 (`vis-05-arena-triple.png`, `measure-triple.png`):** The game band (≈x 484–1444, y 123–663) is a horizontal strip in the upper half; everything below y≈663 besides the collapsed-controls line is dark background, and both side margins are ≈484px deep. The in-canvas HUD text is comfortably legible ("P1 HP 100", "02:00", lobby instructions all readable at this size). This is a presentation-balance issue, not a legibility issue.
- **Minor quirk observed in both triples/native:** the P1 player-HUD block wraps, rendering the score `0` alone on its own line (playerHud P1 is a two-line block "P1 HP 100\n0"). Cosmetic layering/wrapping issue for the graphics owner, visible at every size.
- **390×844 (`vis-05-arena-mobile.png`, `measure-mobile.png`, 6× zoom crop `crop-mobile-hud.png`):** the arena fits horizontally; roughly the bottom 60% of the viewport is empty page background. In the 6× crop the HUD glyphs are visibly fractured by the 0.5594 fractional pixelated downscale (strokes vary 1px/2px, glyphs uneven), "02:00" collides with the scoreboard frame edge and is faint, and "P1 HP 100" occupies ~9 CSS px per line. At DPR 1 in this environment the HUD is borderline legible for reading numbers; fighter labels and score are smaller still.
- **640×360 native:** the full arena including bottom edge fits without scrolling (matches PR #76/#83 assertions; VIS05-01 remains fixed at this SHA).

## Verdict per finding

### VIS05-02 (1920×1080, comparatively small game) — CONFIRMED (measured, non-blocking, design preference)

The disabled space is real and quantified: canvas 960×540 = 25% of the viewport area, 1,555,200 unused px² (75%). The effective CSS scale is 1.5 — a *fractional* pixelated scale — while an integer 2× (1280×720) would fit inside the current chrome (y=123 + 720 = 843 ≤ 1080). Accessibility impact: **none identified at this size** — HUD text measures ≈25–27.5 CSS px per line and was legible in review. This is an aesthetic/layout-balance decision, and it is the owner's to make.

### VIS05-03 (390×844, small in-canvas HUD) — CONFIRMED at measurement level for text size and crispness; PHYSICAL-DEVICE LEGIBILITY — NEEDS PHYSICAL DEVICE

Measured per-line HUD text is 9.3–10.3 CSS px, below any reasonable minimum for primary UI text, produced by a 0.5594 fractional downscale of a 640×360 pixelated canvas — glyph crispness is structurally degraded, which I observed in the zoomed crop. That is an accessibility-class finding based on evidence available in-browser. What remains genuinely unverified: (a) actual device DPR (~3 on a 390-CSS-px phone would triple device pixels, but physical glyph size viewed at handheld distance is unchanged in CSS terms), (b) physical viewing distance, lighting and glare, (c) real browser CSS scaling behaviour on the device. Until a physical check, treat "illegible on device" as plausible but unproven; the ~9px CSS text size and fractional-scale degradation are proven.

## Remediation options (proposal only — not implemented)

### VIS05-02

1. **Integer 2× display option (recommended baseline):** allow `#game` max-width up to 1280px when the viewport permits (e.g. `@media (min-height: 760px)` or a settings toggle "Display scale: Fit / 1× / 2× / integer-fit"). Keeps the 640×360 backing, camera zoom and simulation untouched; fills 1280×720 of 1920×1080, leaving symmetric side margins instead of a small centered strip. Trade-offs: dead space remains at typical desktop aspect ratios (the 16:9 page composition simply isn't wide-format); needs care that the short-viewport rule (`max-height: 540px`) doesn't regress at intermediate window heights; four HUD slots are unaffected because canvas internals don't change.
2. **Explicit fullscreen mode:** a button/keyboard entry to `requestFullscreen` letting the canvas fill the screen (Phaser FIT recalculates). At 1920×1080 the 16:9 canvas is then exactly 1920×1080 — but at a fractional 3× unless snapped to integer scales (3× works on exactly 1080p; every other monitor size needs letterboxing or accepts fractional scale). Trade-offs: closest to "large game", zero layout redesign; requires UI affordance, focus/exit handling, and a decision between "fill" (fractional) and "integer fit with letterbox" (barred edges stay visible).
3. **Scale to available area with splitting the difference:** raise the caps (`main`/`#game`) so the canvas grows with the viewport while preserving aspect (the short-viewport formula already does this by height — extend it by height up to an integer multiple). Trade-offs: canvas grows but stays fractional in most cases (uneven pixel sizes in pixel-art, the same artifact I observed on mobile at 0.56×), and the surrounding page shrinks in usefulness; minimal implementation, but does not deliver integer crispness.

### VIS05-03

1. **Responsive external HUD (recommended):** on small/touch viewports render score, HP and timer, and joining instructions, as DOM text around the canvas with a CSS minimum font size (~12–14px), either instead of or in addition to the in-canvas HUD. Simulation untouched; presentation-only duplication that must be kept in sync with `standings()`. Trade-offs: two HUD renderers to maintain and a divergence risk; hides visual polish (retro scoreboard) on mobile or doubles it; four-fighter slots still fit at narrow widths because the DOM flex wraps.
2. **Minimum font-size rule inside the scene:** detect a small effective CSS scale in `StationScene` and render a large-text HUD variant (e.g. 14–16px scene fonts for mobile), or increase HUD band height on that branch. Trade-offs: still inside the 640×360 canvas, so the *instrument*-size problem is halved, not solved (0.56× downscale remains; 9px→14px scene ≈ 13 CSS px display); larger fonts crowd the 384×216 logical band with four fighter slots; keeps one HUD renderer.
3. **Fix the crispness floor:** increase the render backing resolution on high-DPR/weak-downscale cases (e.g. runtime `VITE_RENDER_WIDTH`-style override or `devicePixelRatio`-aware backing) so text is rasterized above the display scale instead of decimated by 0.56×. Trade-offs: pure presentation (renderSize is already decoupled from simulation), text becomes antialiased/crisper rather than pixel-art style unless paired with pixel-font rendering; mobile GPU memory/perf cost; needs a size/perf check on device.

All options leave `VIEWPORT` (384×216 logical), camera zoom, `Simulation` and the deterministic tests untouched; only CSS/`main.ts` scale plumbing or presentation-layer HUD rendering changes.
