# Single-machine local measurements

This directory holds **local, single-machine** measurements of TurenkiFight's
deterministic simulation and protocol codecs. They are produced by exactly one
command and they are **not** network results.

```sh
npm ci
npm run measure:local
```

The command writes a new `local-<UTC timestamp>.json` (machine-readable) and
`local-<UTC timestamp>.md` (short human summary) here, then prints the summary.
The JSON is the authoritative record; the Markdown file is a rendering of it.
Every committed result file can be regenerated by rerunning the command on a
similar machine. Byte counts are deterministic; timing and resource values are
machine- and load-dependent.

## What each number means

| Field | Meaning |
| --- | --- |
| `codecBytes.inputs.bundledCanonicalPerTick` | UTF-8 bytes of the fixture's single canonical `InputFrame` carrying all four players for one tick. |
| `codecBytes.inputs.perClientCanonical` | UTF-8 bytes of one canonical `InputFrame` carrying one player. Sampled once per client per tick (4 × 7200 samples). |
| `codecBytes.inputs.perClientEnvelope` | The same single-player frame wrapped in a canonical session envelope v1 (`kind: "input"`, `sequence: tick + 1`, no optional `roomId`). |
| `codecBytes.inputs.perClientEnvelopeOverhead` | Measured difference between the envelope and its single-player canonical payload. Includes JSON field names, `sequence`/`targetTick` digits and the envelope's version/kind. |
| `codecBytes.inputs.*BytesPerSecond` | Mean bytes multiplied by 60 Hz. `aggregateUpstreamBytesPerSecond` multiplies the per-client envelope by four clients. |
| `codecBytes.snapshots[].canonical` | UTF-8 bytes of `encodeStateSnapshot` for the state emitted at that snapshot rate. |
| `codecBytes.snapshots[].serverMessage` | The same snapshot wrapped in the prototype WS server message (`kind: "snapshot"`), whose wrapper overhead is measured separately. |
| `codecBytes.snapshots[].bytesPerSimulationTickPerClient` | Canonical snapshot mean × `snapshotHz` / 60. This is the amortized per-tick cost of that snapshot rate for one client. |
| `simulationTicks` | Wall-clock duration of `step(state, inputs)` only, measured with `process.hrtime.bigint()`, once per tick over 7200 ticks. Percentiles are nearest-rank. |
| `snapshotTiming[].encode/decode` | One timed `encodeStateSnapshot` and one timed `decodeStateSnapshot` per emitted snapshot, measured with `process.hrtime.bigint()`. |
| `processResources` | `process.cpuUsage()` and `process.resourceUsage().maxRSS` around the measured 7200-tick loop. `peakRssBytes` is the process lifetime maximum reported by Node (kilobytes converted to bytes), so it includes startup and the loaded fixture. |
| `eventLoopLag` | Opt-in paced timer probe: one fixture tick per 1/60 s through `setTimeout`, with a `monitorEventLoopDelay` histogram. Reported in nanoseconds with its actual sample count. |

Warm-up policy: 600 fixture ticks are replayed from the start on a **separate**
state and discarded before the measured run, which then replays ticks 0..7199
from a fresh state. Snapshot encode/decode paths additionally receive 200
discarded warm-up iterations. No warm-up tick or codec iteration is counted in a
published distribution.

The session envelope measurement omits the optional `roomId`; a room-scoped
envelope is larger by that field. Transport framing (WebSocket frames, WebRTC
DataChannel/SCTP framing, TLS/DTLS) is **not** included in any byte count.

## What these numbers do not mean

- They are **not** network latency, jitter, packet loss, join success, TURN cost
  or bandwidth. The manifest's `network` block is all `NOT_MEASURED` and
  `measuredNetworks` is `0`. No LAN, internet, browser or TURN run was made.
- They are **not** a WebSocket-vs-WebRTC comparison and do not select a
  transport. `scope.transportSelection` is `NOT_A_TRANSPORT_DECISION`.
- They are **not** browser frame pacing, rendering cost or device performance.
  The simulation and codecs run in Node without Phaser or the DOM.
- `processResources.cpuTotalMicroseconds` counts every Node thread, including V8
  helper threads, so it can legitimately exceed the wall clock of the measured
  single-threaded loop. Compare runs on the same machine, not across machines.
- The event-loop probe includes the platform timer floor: legacy Windows timers
  quantise to roughly 15.6 ms. Treat the value above that floor as the signal,
  not the floor itself. It is a harness timer measurement, not a browser
  rendering measurement.
- Timing distributions are sensitive to CPU frequency scaling, background load
  and Node version. Only the encoded byte counts are deterministic.
- A single run, or two runs on one machine, cannot justify a network topology
  decision. The transport decision also depends on the literature review and
  the explicit owner criteria.

## Provenance required in every result

Each JSON records:

- the exact command (`npm run measure:local`) and the measurement-affecting CLI
  flags;
- Node version, OS platform/release/architecture, CPU model and logical core
  count;
- git commit SHA, whether the working tree was dirty, and the exact
  `dirtyExclusions` list;
- fixture SHA-256 and seed;
- measured tick count, warm-up policy and every sample count;
- the measurement methodology literals.

`workingTreeDirty` ignores only generated output under `benchmarks/results/`;
that single prefix is recorded in `dirtyExclusions` and the validator requires
exactly that list. A modified simulation, protocol, harness or test file still
marks the run dirty, so a clean result always means the recorded commit is the
code that ran.

No private IP address, hostname, user name or absolute path is written. The
`--out` flag is intentionally excluded from the recorded argument list.

### Evidence limitation

The manifest is internally consistent but not provenance-verified. Raw samples
are not stored, so a coherently edited manifest cannot be distinguished from a
real run. If stronger evidence is ever needed, raw samples must be archived
outside the repository or the manifest must be signed at write time.

## Reproducing and adding a result

```sh
npm ci
npm run measure:local                                  # default: 7200 ticks, 600 warm-up
npm run measure:local -- --ticks=7200                  # explicit
npm run measure:local -- --event-loop=off              # skip the paced probe
```

Keep both the `.json` and `.md` for a committed result; the JSON schema is
validated at write time by `benchmarks/local/manifest.ts`. The test suite
requires committed results under this directory to use the full 7200-tick
default; write shorter exploratory runs elsewhere with `--out=<path>`. Do not
edit a result file by hand. If a number is not produced by this command on the
recorded machine, it must not appear in this directory.
